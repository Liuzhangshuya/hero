## 0. 先看这里：三条硬规矩

1. **旧工程冻结**
   - 把当前整个目录复制一份（或在 git 里打 tag），命名如 `hero-baseline-20260318-golden`。
   - 这是"随时能烧回去"的保险，不参与重构。
   - 保留一份**确认能动的 hex**，并记录烧录日期。

2. **新旧并存，按模块切换**
   - 同一个模块，旧实现和新实现**不要同时参与编译**（函数名会重名）。
   - 在 `Src/freertos.c` 里按模块切换任务入口，一次只切一个模块。
   - 每次提交（commit）都必须是一个"能动的版本"。

3. **先适配层，后改调用方**
   - 新模块先保持旧的函数名/旧结构体（shim），让旧代码零改动地继续跑。
   - 等新模块实车验证通过，再逐个替换调用方，最后删旧文件。

> 反例（不要做）：一次性把 `application/` 全换成参考工程，然后花两周修编译错误——这期间车不能动，也没法回滚。

## 2. 推荐迁移方式：旁路并存 + 适配层

### 2.1 目录策略

```
D:\RM\
  hero-baseline-20260318-golden\   ← 冻结，只用来烧回
  hero-standardpp\                 ← 重构工作区（从 golden 复制）
```

不要直接在 `D:\RM\StandardRobotpp-master` 上改，也不要直接在当前目录上"大爆炸式"替换。

### 2.2 适配层（shim）思想

新模块内部用 StandardRobot++ 的 `Motor_s` / `data_exchange` / 八步流程；
对外**暂时保留旧函数签名**，让旧调用方一行不改。

示例（CAN 层替换后，供旧云台代码继续使用）：

```c
/* 新 CAN 层内部已用 GetDjiMotorMeasurePoint */
const motor_measure_t * get_yaw_gimbal_motor_measure_point(void)
{
    static motor_measure_t m;
    const DjiMotorMeasure_t *p = GetDjiMotorMeasurePoint(2, 0); /* CAN2, 0x205 */
    m.ecd           = p->ecd;
    m.speed_rpm     = p->speed_rpm;
    m.given_current = p->given_current;
    m.temperate     = p->temperate;
    m.last_ecd      = p->last_ecd;
    return &m;
}
```

> 注意：不要用指针强转。旧 `motor_measure_t`（5 字段）和新 `DjiMotorMeasure_t`（多一个 `last_fdb_time`）布局不同，显式赋值最稳。

### 2.3 单模块切换四步法

1. **新文件进工程但不编译**（Keil 里先不加组，或加组后 `Exclude from build`）。
2. **同一提交内**：新实现 + shim 加入编译，旧实现移出编译组。
3. **台架 → 架空 → 落地**，逐级验证。
4. **验证通过后**，再删旧文件、更新调用方。

## 4. 接口级对照

### 4.1 CAN / 电机层（🔴 最高风险，先做）

#### 4.1.1 电机对象映射

参考框架的 `MotorInit` 签名：

```c
void MotorInit(Motor_s *p_motor, uint8_t id, uint8_t can,
               MotorType_e motor_type, int8_t direction,
               float reduction_ratio, uint16_t mode);
```

> **关键**：`id` 不是 CAN StdId，而是 DJI 的"电机编号"：
> - M2006 / M3508：反馈 StdId = `0x200 + id`（id 1~8）
> - GM6020：反馈 StdId = `0x204 + id`（id 1~7），发送帧 id 1~4 → `0x1FF`，id 5~7 → `0x2FF`

对应到你们的车：

| 执行机构 | 旧取点函数 | 旧 CAN/ID | 新 `MotorInit(...)` | 新发送 |
|---|---|---|---|---|
| 底盘 M1 | `get_chassis_motor_measure_point(0)` | CAN1 `0x201` | `id=1, can=1, DJI_M3508` | `CanCmdDjiMotor(1, 0x200, ...)` |
| 底盘 M2 | `get_chassis_motor_measure_point(1)` | CAN1 `0x202` | `id=2, can=1, DJI_M3508` | 同上 |
| 底盘 M3 | `get_chassis_motor_measure_point(2)` | CAN1 `0x203` | `id=3, can=1, DJI_M3508` | 同上 |
| 底盘 M4 | `get_chassis_motor_measure_point(3)` | CAN1 `0x204` | `id=4, can=1, DJI_M3508` | 同上 |
| 云台 yaw | `get_yaw_gimbal_motor_measure_point()` | CAN2 `0x205` | `id=1, can=2, DJI_M6020, DJI_VOLTAGE_MODE` | `CanCmdDjiMotor(2, 0x1FF, yaw, pitch, ...)` |
| 云台 pitch | `get_pitch_gimbal_motor_measure_point()` | CAN2 `0x206` | `id=2, can=2, DJI_M6020, DJI_VOLTAGE_MODE` | 同上 slot2 |
| 拨弹 2006 | `get_T_2006_measure_point()` | CAN2 `0x207` | `id=7, can=2, DJI_M2006` | 同上 slot3（**注意同帧**） |
| 拨弹 3508 | `get_trigger_motor_measure_point()` | CAN1 `0x205` | `id=5, can=1, DJI_M3508` | `CanCmdDjiMotor(1, 0x1FF, trigger, ...)` slot1 |
| 摩擦轮 R | `get_R_3508_measure_point()` | CAN1 `0x206` | `id=6, can=1, DJI_M3508` | slot2 |
| 摩擦轮 L | `get_L_3508_measure_point()` | CAN1 `0x207` | `id=7, can=1, DJI_M3508` | slot3 |

> `direction`（1/-1）和 `reduction_ratio`（3508/2006 填 19/36，6020 填 1）必须按实车标定填写，**不要照抄参考 hero 参数**。

#### 4.1.3 反馈/离线

- 参考版在 `DjiFdbData()` 里写 `last_fdb_time`，`GetDjiFdbData()` 里用 `MOTOR_STABLE_RUNNING_TIME` 判离线。
- `MotorInit()` 会把电机指针加入全局 `MOTORS[]`，`ScanOfflineMotor()` 统一扫描。
- 旧代码依赖 `detect_hook(TOE)`，新代码可以用 `Motor_s.offline`；**两种机制都要接**，否则报警/保护会漏。

#### 4.1.4 🔴 CAN2 `0x1FF` 同帧冲突（必须提前设计）

现状：CAN2 `0x1FF` 一帧同时承载 **yaw + pitch + 2006 拨弹**，由 `gimbal_task.c` 统一发送。

参考框架：`gimbal_yaw_pitch_direct.c` 的 `GimbalSendCmd()` 只发 yaw/pitch，第 3、4 槽填 0；`shoot_fric_trigger.c` 的 `ShootSendCmd()` 另外发拨弹。若直接把两个任务并行跑：

- 两个任务都会往 CAN2 `0x1FF` 写；
- 后发的会把先发的**整帧覆盖**，表现为云台或拨弹随机失效。

处理方案（按改动量排序）：

| 方案 | 做法 | 适用 |
|---|---|---|
| **A（推荐，过渡期）** | 拨弹仍由云台任务统一发：`CanCmdDjiMotor(2, 0x1FF, yaw, pitch, trigger, 0)` | Phase 4 之前 |
| B | 做一个 CAN 发送仲裁层：所有帧集中在一个任务/函数里发 | Phase 5 之后 |
| C | 改硬件 ID，把拨弹移出 `0x1FF` 帧 | 有条件再做 |

#### 4.1.5 超电协议冲突（⚠）

| 项 | 当前 SDK | 参考框架 |
|---|---|---|
| 接收 StdId | `0x052` | `0x211` |
| 发送 StdId | `0x061` | `0x210` |
| 数据结构 | `SuperCap_Control_t` / `SuperCap_Feedback_t` | `SupCap_s` / `SupCapMeasure_s` |
| 物理量单位 | SDK 内部已换算 | `voltage_in / 100`、`current_in / 50` |

**结论：先确认车上超电板用的是哪套协议。** 若板子就是现在的 SDK，保留 SDK，在 `CAN_receive.c` 里把 `0x052` 分支接回 `SuperCap_ParseRxData()` 即可；不要为了"框架统一"换掉能用的协议。

## 7. 风险清单

| 等级 | 风险 | 后果 | 规避 |
|---|---|---|---|
| 🔴 | CAN2 `0x1FF` 同帧：云台与拨弹分属两个任务后互相覆盖 | 云台或拨弹随机失效 | 过渡期保持"云台任务统一发"（4.1.4 方案 A） |
| 🔴 | 拨弹电机型号不确定（3508 / 2006 / 双路） | PID、限幅、发送槽位全错 | 实车确认后再写参数 |
| 🔴 | 云台零点/限位从 Flash 标定换成宏 | 上电打限位、烧电机 | 先保留 Flash 标定（4.3.4） |
| 🔴 | 超电协议不匹配（0x052/0x061 vs 0x211/0x210） | 超电不工作或误动作 | 先确认板子协议（4.1.5） |
| 🟡 | 底盘参数单位不同（RPM vs m/s、rad/s） | 车跑飞/没力 | 重新换算 + 台架重调 PID |
| 🟡 | `detect_task` 未启用 | 失联保护失效 | Phase 2 打开 |
| 🟡 | `referee_usart_task` 未启用 | 功率/热量保护失效 | Phase 5 前打开 |
| 🟡 | 自瞄依赖 USART1 IDLE，迁移时漏接 | 自瞄失效 | 保留 `Usart1Receive_IDLE` 与 `AUTO_control_init` |
| 🟡 | 参考工程 `warning as error` | 编译被警告卡死 | 先解决警告，不要关开关 |
| 🟢 | 参考 hero 参数不是你们的 | 直接烧会参数全错 | 只当模板，逐项核对 |
| 🟢 | `test_task` weak/strong 冲突 | 报警不响 | 检查链接与源文件分组 |
